## Actual commands and state, not guessed APIs
- Body Settings invokes the existing local `PUT /api/affiliates/admin/rates` client alias, which maps to mounted `POST /api/affiliates/commands/commission-settings` and the reviewed BFF route.
- Health Settings invokes mounted `POST /api/integrations/body/commands/commission-settings` directly through its isolated journal adapter.
- Both read the same authoritative `/api/integrations/body/commands/state/{affiliateId}`; Body exposes it at `/api/affiliates/commands/state/{affiliateId}`. Recovery uses the matching mounted `commission-settings/{commandId}` status route. No new API route, financial ledger or synchronization database was introduced.
- The command envelope preserves `version:1`, UUID `commandId`, `expectedVersion`, and explicit `payload.rates`. The service binds receipts to the current canonical actor, independent of portal. Client namespaces are only journals, not authorization.
- Configuration **committed** and provider tasks **pending/blocked** are distinct. Recovery verifies the committed receipt before allowing an explicitly separate operation. Saving terms never claims a usable target checkout code.

## Explicit policy and preserved values
The form exposes direct, recurring, referral and customer discount percentages; referral basis; effective local date/time serialized as UTC; product IDs; one-time and/or subscription purchases; subscription cycle limit (explicit 0 = unlimited); customer eligibility; and each order/product/shipping combination choice. Blank is not zero. No one-time/no-stacking default is selected. Existing Health peptide values are unchanged unless an admin explicitly submits peptide terms.

The existing Basic Shopify provider currently supports all customers only, requires equal customer-discount/checkout policy between its two Shopify categories, and cannot provision a zero-discount code. It can store differing category commissions and explicit zero agreements. Unsupported/missing terms remain blocked; settings do not silently equalize them or substitute Health15%. Supporting unequal checkout discounts/restricted audiences requires separately qualified provider capability. Future terms do not apply early; saving does not reprice historical earnings. This technical behavior is **not approval of a historical-import/no-backfill business policy**. No historical import or repricing was requested or executed.

## Latest automation correction — precise integration boundary
The requested middleware is **bidirectional signaling**, not just dashboard parity and not bidirectional database/policy replication:
1. Existing Health automation creates/verifies a Woo affiliate code → durable middleware event → same code text/canonical affiliate on Shopify, using **Shopify's own Settings policy**.
2. Body/Shopify origin → durable middleware event → same canonical affiliate/code on Woo, using **Health's own policy**.

This Settings commit does **not** claim those external-origin event hooks are implemented or active. It leaves the working Health automation unchanged. Exact inspected attachment points:
- Existing Health helper `lib/affiliates/coupon-sync.ts`: `syncAffiliateCoupons` calls private `createOrUpdateCoupon` after `fetchCouponByCode`. Legacy `created/updated` responses currently lack a verified provider-ID readback; do not treat their HTTP success as a durable source event. Smallest safe additive integration is an isolated post-success verification/emission seam, preserving the helper's existing Woo behavior/credentials/rates, and a durable retryable observation receipt. Existing verified `ok` observations can reconcile delivery gaps without recreating codes. Do not attach activation to read-only dry-run requests.
- Canonical candidate `lib/integrations/body/commands/service.ts`: `codes()` already queues separate `public-code` tasks per target store with distinct payload terms; `enqueue()` has affiliate/store/version/operation uniqueness. `outbox.ts` performs provider ownership/readback/recovery. These are reusable target-delivery building blocks, **not an external Woo↔Shopify event receiver**. Existing `creator-code-sync` POST is an admin command, not permission to invent a webhook or bypass receiver authentication.
- For actual installed Woo/Shopify automation outside these source helpers, verify the real emission seam first. No uninspected plugin hook or webhook endpoint is claimed mounted.

Required minimal event boundary (not a guessed deployed DTO): authenticated source identity/store/object ID, stable source event/revision ID, canonical affiliate ID, code text, causation/root event ID and observed time. Do **not** transport source rates/discounts as target policy. Persist source receipt before acknowledging delivery; dedupe receiver by source/event/target; freeze target Settings version; check canonical ownership/collisions and source provider readback; suppress reflected events using causation and verified target ownership; retain uncertain writes for readback, not blind retry. Missing target settings stay `pending_configuration`; an event `queued` is never `target_code_confirmed`. Existing source automation must remain successful even when target delivery is pending.
